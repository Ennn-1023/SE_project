# SE Project Constitution

本文件為學生專題「SE Project」的開發憲章，規範所有功能的設計、實作、測試與交付方式。

## Core Principles

### I. 輸入驗證（不可妥協）

- 每個功能凡接收外部輸入（使用者輸入、API 請求參數與 body、檔案、環境變數、CLI 參數），
  都 MUST 在使用前進行驗證，包含：必填欄位、型別、格式、長度或數值範圍、允許值清單。
- 驗證 MUST 在系統邊界（進入點）完成；不可假設上游已驗證。
- 驗證失敗時 MUST 拒絕該輸入並中止處理，不得以靜默修正或預設值掩蓋錯誤
  （除非規格明確定義了預設值）。

**理由**：未驗證的輸入是錯誤與安全漏洞最常見的來源；在邊界統一驗證可讓內部邏輯保持單純。

### II. 清楚的錯誤訊息

- 每一種驗證失敗或執行錯誤 MUST 產生清楚的錯誤訊息，至少說明：
  哪個欄位或操作出錯、為何出錯、使用者可以如何修正。
- 錯誤訊息 MUST NOT 包含機敏資料（密碼、金鑰、token、個資）或內部堆疊追蹤（stack trace）
  給終端使用者；詳細技術資訊只可寫入不含機敏資料的 log。
- API 型功能 MUST 使用一致的錯誤格式與合適的狀態碼（例如 HTTP 400 表示輸入錯誤）。

**理由**：清楚的錯誤訊息能讓使用者自行修正問題，也讓組員與評審更容易除錯與驗收。

### III. 機敏資料只放環境變數（不可妥協）

- 機敏資料（密碼、API 金鑰、token、資料庫連線字串、私鑰等）MUST 只透過環境變數提供。
- 機敏資料 MUST NOT 寫入原始碼、設定檔、測試檔、文件、commit 紀錄或任何 log 輸出。
- 專案 MUST 提供不含真實值的範例檔（例如 `.env.example`）列出所需環境變數名稱；
  實際的 `.env` 檔 MUST 列入 `.gitignore`。
- 程式啟動時若缺少必要的環境變數，MUST 以清楚的錯誤訊息指出缺少的變數名稱（不含其值）並停止。
- 記錄 log 時若可能涉及機敏欄位，MUST 先遮罩或移除。

**理由**：機敏資料一旦進入版本控制或 log 就難以完全清除，會造成無法挽回的外洩風險。

### IV. 正常案例與邊界案例測試（不可妥協）

- 每個功能 MUST 至少具備：
  - 一個正常案例（happy path）測試，驗證合法輸入得到預期結果；
  - 一個邊界案例測試，例如空值、最小／最大值、長度上限、格式錯誤或不合法輸入。
- 原則 I 的輸入驗證與原則 II 的錯誤訊息 MUST 至少有一個測試覆蓋（驗證被拒絕且訊息正確）。
- 測試 MUST 可自動執行且不依賴真實機敏資料；需要憑證時使用測試用的假值或 mock。
- 功能在所有測試通過前 MUST NOT 視為完成。

**理由**：正常案例證明功能可用，邊界案例證明功能可靠；兩者皆是驗收的最低標準。

### V. 回報測試指令與結果

- 每個功能或任務完成時 MUST 回報：
  - 執行測試的確切指令（可直接複製執行）；
  - 實際執行結果（通過／失敗數量，以及失敗時的錯誤輸出摘要）。
- 結果 MUST 如實回報；不得在未實際執行的情況下宣稱測試通過。若有測試被跳過，MUST 說明原因。

**理由**：可重現的測試指令與真實結果，讓組員、助教與評審能獨立驗證成果。

## 安全與資料處理要求

- 相依套件 MUST 來自官方或可信任的套件來源，並鎖定版本（使用 lock 檔）。
- Log MUST 只記錄除錯所需的資訊；不得記錄密碼、token、完整個資或環境變數的值。
- 提交程式碼前 MUST 檢查 diff，確認沒有機敏資料被加入。
- 測試資料 MUST 使用虛構資料，不得使用真實使用者資料。

## 開發流程與品質關卡

- 功能開發流程：規格（spec）→ 計畫（plan）→ 任務（tasks）→ 實作 → 測試 → 回報。
- 每個功能的規格與計畫 MUST 列出：輸入欄位及其驗證規則、錯誤情境與對應錯誤訊息、
  所需環境變數、正常案例與邊界案例測試清單。
- 合併到 `main` 前的品質關卡（全部 MUST 通過）：
  1. 所有輸入皆有驗證，且錯誤訊息清楚（原則 I、II）；
  2. 無機敏資料出現在程式碼、設定檔或 log（原則 III）；
  3. 每個功能至少有正常案例與一個邊界案例測試，且全部通過（原則 IV）；
  4. 已回報測試指令與實際結果（原則 V）。

## Governance

- 本憲章優先於專案內其他開發慣例；若有衝突，以本憲章為準。
- 修訂程序：任何組員可提出修訂，須說明修訂內容與理由，經組員討論同意後更新本檔，
  並同步更新版本號與「Last Amended」日期。
- 版本規則（語意化版本）：
  - MAJOR：移除原則或以不相容方式重新定義原則；
  - MINOR：新增原則或章節，或實質擴充規範；
  - PATCH：文字澄清、錯字修正等不影響語意的修改。
- 合規檢查：每次程式碼審查與功能驗收 MUST 依「開發流程與品質關卡」逐項檢查；
  任何例外 MUST 在對應的 plan 中記錄理由。
